# The turn-execution model: analysis and direction call

Status: reference analysis, 2026-07-07. Covers the server's turn pipeline (`server/routes/talk.py`, `server/pi_runner.py`, `server/chats.py`, `server/config.py`) against ADRs 0002, 0005, 0007.

## 1. The model in one statement

A turn is one held-open HTTP request that does everything: `POST /api/talk` acquires a per-chat `asyncio.Lock` (`talk.py:31`, `talk.py:79-81`), and inside that lock it evicts the previous turn's audio (ADR 0005, `talk.py:83`), transcribes the upload with faster-whisper, launches a **one-shot pi subprocess** (`pi -p --mode json --session <id> --extension pi/tools.ts`, `pi_runner.py:112-133`) with a hardcoded 120-second timeout (`pi_runner.py:13`), parses pi's NDJSON events for the reply text, persists the turn, synthesizes TTS, and returns everything in the response body. Turns on different chats run concurrently (the subprocess runs via `asyncio.to_thread`); turns on the same chat serialize on the lock, relying on CPython's documented FIFO waiter order (`talk.py:26-30`).

State is two-tier. The server's own state is module-global dicts: `_chats` / `_turns` (`chats.py:35-36`), `_talk_locks` and `_chat_audio_files` (`talk.py:31,36`), loaded once at import (`app.py:19`) and persisted by rewriting **one JSON file in full** on every mutation (`save_chats()`, `chats.py:65-83`; atomic via temp-file + `os.replace`). But the conversational context the LLM actually sees lives in **pi's own session store**, referenced only by `chat.pi_session_id` (`chats.py:30`, replayed via `--session` at `pi_runner.py:125-126`). The server's turn list is display history and the source of truth for clients (ADR 0007); pi's session file is the source of truth for the model. Those are two different stores that can diverge (see section 2c).

## 2. The load-bearing decisions, and whether they cohere

### a. The "queue" is a fair lock under an open socket, and ADR 0002 says otherwise

ADR 0002 states: "Every submission is accepted immediately and processed as an independent turn ... This replaces two things: the server's per-chat lock, which previously just made the caller wait ..." (`docs/adr/0002-turn-submission-queue.md:3`). The implementation **is** a per-chat lock that makes the caller wait: the handler acquires `_talk_locks[chat_id]` with the client's request held open for the entire turn (`talk.py:79-81`). The code comment even cites ADR 0002 as justification for the lock (`talk.py:30`). What the fix evidently replaced (inference from the ADR's own text) was the iOS client's single-slot `pendingText`, which genuinely dropped messages; server-side, the mechanism the ADR says was replaced is the mechanism that shipped. The ADR is not merely loosely worded: its central claim about the server is false.

What the drift costs, concretely:

- **A "queued turn" is a blocked in-flight HTTP request.** It exists only in a socket and an `asyncio.Lock` waiter list. A server restart drops every waiter, including the uploaded audio, which is only written to disk inside the lock (`talk.py:118-119`). So "nothing you say is dropped" (README, ADR 0002 headline) holds only within one process lifetime and one socket lifetime.
- **The timeout arithmetic can violate the guarantee with no restart at all.** pi's per-turn cap is 120s (`pi_runner.py:13`); the iOS client times out after 180s of response silence (`ios/.../ServerClient.swift:13`, `timeoutIntervalForRequest = 180`). A turn queued behind a single turn that runs to the pi timeout plus TTS waits over 120s before its own work even starts; two-deep queueing arithmetically exceeds 180s. On client timeout, uvicorn most likely cancels the handler task (inference: standard uvicorn behavior on disconnect before response start, not verified against the pinned version), and the queued turn evaporates: never transcribed, never persisted. The FIFO tests can't see this; it's a wall-clock property.
- **A cancellation mid-pi is worse than a drop.** If the handler is cancelled while pi runs, the thread and subprocess keep going (threads aren't cancellable); pi appends the exchange to *its* session file, but `add_turn` never runs. Next turn, the model remembers an exchange the user never saw and the turn history doesn't contain. This is inference from the code structure (`pi_runner.py:142` await point vs. `talk.py:192` persistence), not an observed bug, but nothing prevents it.

Does this matter at this project's scale? Mostly no. One user, one Mac Mini, turns rarely stack two deep, and the recovery is re-tapping the mic. The lock is *simpler and better-tested* than a real queue would be. The problem is not the mechanism; it's that the written guarantee is stronger than the mechanism, in a repo whose stated process is spec-first and whose maintainers are largely agents that read the ADRs as ground truth. An ADR that asserts durability the code doesn't have is the most expensive kind of doc in this repo.

### b. The JSON-rewrite datastore is an unexamined default, not a decided boundary

`save_chats()` serializes every chat and every turn ever recorded and rewrites the whole file, and it runs **up to three times per turn**: when pi reports a session id (`pi_runner.py:155-157`, unconditionally on every run, even when the id is unchanged), inside `add_turn` (`chats.py:88`), and at the end of the handler (`talk.py:209`). There is no ADR for any of this; the eight ADRs cover audio, failure, tools, and sync semantics, never persistence. Two further signs it was assembled rather than decided: `TURNS_FILE` is defined in config (`config.py:47`) and imported by `chats.py:12` but never used (turns actually live inside `CHATS_FILE`), and a corrupt file is handled by logging a warning and starting empty (`chats.py:57-62`): total, silent-to-the-user loss of all turn history. pi's sessions survive separately, so LLM context quietly outlives the visible history, the two-store divergence again.

The performance ceiling is genuinely distant: at voice cadence (a few KB per turn, thousands of turns before this is even measurable), an O(total-turns) JSON dump costs milliseconds against a multi-second pi call, and the atomic-replace write is crash-safe. That part is fine and should not be "fixed."

The real load-bearing fact is hidden underneath: **module-global dicts plus whole-file rewrite means exactly one server process, forever.** A second uvicorn worker would fork the dicts, split the locks (making ADR 0002's ordering false even locally), and race the file. Nothing currently runs multi-worker (`run.sh` and the launchd plist use default single-worker uvicorn; asserted from the run commands, not from an exhaustive deployment audit), but the invariant is written nowhere. It is the strongest unstated assumption in the codebase.

### c. One-shot subprocess per turn: the keystone, and it holds

Each turn pays node startup, extension load, and pi's replay of its session (`pi_runner.py:112-133`). Note what it does *not* pay relative to RPC mode: the LLM context re-send is identical either way, since pi replays the session to the model per request regardless. The real per-turn overhead is process spin-up (seconds at most), and the real cost is **capability**: no steer, no abort, no mid-turn event stream, no progress signal during a silence that can legally last 120 seconds. What it buys: total crash isolation (a wedged pi dies with its timeout; there is no daemon to health-check, restart, or leak), a server that holds zero process state between turns, and a shape that composes exactly with the lock (one subprocess at a time per chat, trivially).

Coherence verdict for the trio: the lock, the one-shot subprocess, and the rewrite-everything datastore are **mutually reinforcing**. All three are the same bet: one turn at a time, no resident state, one process. The code is internally coherent. The incoherence is exclusively between the documents and the code: ADR 0002's queue framing, the missing persistence ADR, the undocumented single-process invariant, and the vestigial `TURNS_FILE`.

## 3. Open decisions, ranked by cost of deciding late

**1. Make the written model true (highest cost of lateness).** Amend ADR 0002 to say what ships: a fair per-chat lock, request held open, never-dropped scoped to process-and-socket lifetime, with the 120s/180s timeout interaction stated. Write the missing persistence ADR: single JSON file, atomic rewrite, corrupt-file-starts-empty, and above all the single-process invariant. Delete the `TURNS_FILE` vestige while there. Cost of lateness compounds daily: this repo is maintained by agents instructed to treat ADRs as spec, so every day the false queue claim stands, work can be built on a durability guarantee that doesn't exist. Cost of fixing: an afternoon of prose. Stakes-to-effort ratio is unmatched by anything else here.

**2. Scope turn durability explicitly (decide the *policy* now, build nothing).** Options: (a) accept socket-lifetime durability and say so; the client's recovery path already exists, since ADR 0007's replace-on-fetch means a client that timed out mid-turn reconciles on next load *if the turn was persisted*. Or (b) a durable inbox (accept upload, return 202, client polls or is pushed): real work, a client-contract change, and a solution to a problem one user on a LAN has not had. Choose (a) and write it down. The dangerous middle is choosing nothing: the cancellation-mid-pi divergence (section 2a, third bullet) is the one failure here that corrupts state rather than losing a request, and whether it's acceptable should be a decision, not an accident. Cost of deciding late: moderate. It's cheap until the demo server or a second user makes restarts-under-load routine.

**3. Long-lived `pi --mode rpc` per chat (defer, with named triggers).** What it unlocks: steer (ADR 0002's deferred option, the only feature in the written record that *requires* it), abort, mid-turn events, and shaving process spin-up off latency. What it costs: a resident child process per chat with lifecycle management (spawn, health, restart, orphan cleanup on server restart), a persistent protocol replacing one `subprocess.run`, loss of per-turn crash isolation, and a rework of the lock model (steer replaces queueing rather than sitting beside it). ADR 0002 was right to defer it, and the deferral should stay until one of these signals appears: (a) real usage shows people talking over in-progress turns and finding wait-then-answer wrong, i.e. actual steer demand, not hypothesized; (b) abort becomes necessary (a runaway 120s turn you can't stop is a real voice-UX wound if it starts happening); (c) pi spin-up becomes a measured, noticeable fraction of turn latency. Cost of deciding late is genuinely low: the subprocess call is contained in `pi_runner.run_pi` with one call site (`talk.py:166`), so nothing accretes around it, *provided* the response shape (`transcript/reply/audio_urls`) doesn't get further entrenched in clients in ways a streaming model would break. That proviso is the one thing to watch while deferring.

**4. Datastore ceiling (defer indefinitely).** SQLite becomes right if, and only if, multi-process becomes necessary or turn counts make the in-lock rewrite measurable. `chats.py` encapsulates load/save behind four functions; migration is mechanical whenever it's wanted. The only prep worth doing now is free: it falls out of writing the persistence ADR in item 1. One micro-fix worth taking opportunistically: `pi_runner.py:155-157` rewrites the file even when the session id hasn't changed; guard it with `if new_sid != chat.pi_session_id`.

## 4. Verdict

**The model holds. Keep it, and make the paper match it.** One-shot subprocess plus per-chat fair lock plus atomic whole-file JSON is the correct amount of machinery for one person speaking to one machine, and the three choices reinforce each other; every alternative on the table trades that coherence for daemon-state complexity solving problems that have not yet occurred. The RPC move should happen the day steer or abort has a demonstrated user, and not a day sooner.

The two things that matter next:

1. **Re-true the record**: amend ADR 0002 to describe the lock (with its restart and timeout scope), and write the one missing ADR, persistence and the single-process invariant. In an agent-maintained, spec-first repo, a false ADR is the highest-interest debt there is, and this one is load-bearing.
2. **Decide the durability policy on purpose** (recommend: accept socket-lifetime durability, rely on ADR 0007 reconciliation, and document the cancellation-mid-pi divergence as a known, tolerated edge), so that when the RPC trigger eventually fires, it's pulled by a signal against a spec that's true, not by drift against one that isn't.
